## Goal

Validate every real consumer-facing promise of `go-oci-blob` through a disposable external harness without modifying the library under test. Then apply one consistent campaign to major hosted and self-hosted registries, record the compatibility matrix, and retain only the repeatable test assets worth maintaining.

## Outcome

Goal met. The initial immutable-source consumer campaign exercised build and existing tests, real Registry 2 and Zot instances, TLS and authentication, protocol faults, retry and resume behavior, integrity failures, redirects and credential isolation, upload modes, Mount, cancellation, shared-client concurrency, large streaming transfers, connection reuse, and cleanup. The positive suite passed 32 top-level tests and 118 test nodes; focused protocol and resource race campaigns passed; and 648 mixed shared-client operations across `GOMAXPROCS=1,2,8` completed without a race, deadlock, or data mix-up. No functional data-integrity, reliability, streaming, concurrency, or resource-lifecycle defect was found.

The campaign found one actionable public-contract issue: `WithProgress` implied callback serialization across concurrent transfers, while the implementation serializes callbacks per transfer. PR #24 clarified the API and design contract, made the public progress test recorder race-safe, and was squash-merged as `8700a0989bb82ca272ca986e2dc8eae79536d1b5` after all checks passed.

Coordinated campaigns then characterized Amazon ECR Private, GHCR, Docker Hub, the Artifact Registry-backed `gcr.io` URL, Quay.io, Azure Container Registry, Harbor, GitLab's native registry, and Nexus Repository OSS 3.76.0. Core authenticated reads, ranges, parallelism, resume, monolithic uploads, concurrency, and Location handling passed across all nine. Registry-specific limits were reproduced for empty blobs on ECR, GHCR, GCR, and Quay; chunked uploads at the tested payload and chunk configurations on ECR and GCR; and wrong-digest rejection, exact-size rejection, and cross-repository Mount on Nexus. ECR Mount passed after the regional account setting was explicitly enabled. The dated matrix and evidence identities are preserved in `REGISTRY_TEST_RESULTS.md`.

The disposable campaigns proved useful enough to retain a minimal provider-neutral harness. PR #25 added a nested consumer module under `test/`, 20 evidence probes, independent raw and ORAS controls, conservative normal/race aggregation, redacted reports, focused tests, Moon integration, a pinned ORAS control, and an agent-operated provider runbook. Provider SDKs, credentials, Compose manifests, and registry lifecycle automation remain disposable. PR #25 was squash-merged as `401ad8a5ab3a886107e1d974302cecbb18c3d545`; all post-merge CI, CodeQL, Pages, Release Please, and dependency-graph runs passed.

The campaign notes record cleanup and absence checks for every specifically named hosted repository, package, robot, scoped token, local registry deployment, container, network, volume, credential file, fixture, and evidence directory. A final local audit found no campaign temporary directory or container; only unrelated GitHub MCP containers remain. The ECR `BLOB_MOUNTING` setting remains enabled by explicit request. Local `master` is clean and synchronized with `origin/master`; both feature branches and Worktrunk worktrees are gone.

## Key Decisions

- Test from an immutable external consumer module -> this prevents tests from compensating for or reaching into the library under test and makes raw HTTP and ORAS useful independent oracles.
- Clarify progress callback serialization as per-transfer -> global function serialization is not implementable with sound function identity semantics and would couple unrelated transfers; callers sharing callback state across transfers must synchronize it.
- Require fresh repositories, independent bytes and digest checks, and repeated `NO` outcomes -> HEAD responses, unreferenced visibility, and upload cleanup behavior vary enough that library-only round trips create false confidence.
- Treat infrastructure, authentication, and ambiguous transport failures as invalid campaigns rather than registry capability results -> only causal, independently verified behavior may become `PASS`, `NO`, or `BLOCKED`.
- Keep the committed harness registry-neutral -> provider provisioning, secret retrieval, local deployment topology, version selection, and cleanup change too quickly and are better regenerated by a capable agent from a strict runbook.
- Keep live registry campaigns out of CI -> routine CI owns fast format, lint, build, unit, race, and local E2E checks; credentialed corpus refreshes remain deliberate operator actions.

## Open Threads

- Publish a user-facing compatibility matrix from the journal ledger when desired; the merged PR intentionally added the refresh procedure, not a potentially stale claims table.
- Refresh live results before relying on them for defaults or documentation. Registry behavior, account policy, and product versions can change independently of this library.
- Treat the ledger as historical characterization from an evolving disposable harness. Before publishing it as an authoritative compatibility reference, rerun every target with the merged harness so all rows use the same exact Pull, range-boundary, header-isolation, and safety assertions; raw campaign evidence was intentionally removed after recording its hashes.
- Natural throttling retry and parallel range-ignored fallback were not triggered by the live registry corpus, so those matrix rows remain `N/A`; deterministic consumer tests cover the library paths.
- `RetryPolicy.MaxAttempts` wording remains ambiguous between a whole transfer and each logical range request, and the design's advertised-range gate for broken-stream resume is stale in a reliability-positive direction. Neither produced a functional failure in this session.
- Amazon ECR Private `BLOB_MOUNTING` remains `ENABLED` in the shared account's `us-east-2` registry by explicit user choice.

## Lessons

- A registry's successful upload status or HEAD response does not prove consumers can retrieve the bytes; exact raw GET, independent hashing, and ORAS controls exposed several otherwise invisible incompatibilities.
- Mainstream container clients do not exercise every Distribution API path. Empty blobs, chunked uploads, exact-size rejection, wrong-digest cleanup, and Mount need direct live proof before becoming product claims or defaults.
- The durable boundary is evidence logic and result aggregation, not cloud lifecycle code. A precise runbook plus small provider-neutral engine preserves repeatability with substantially less provider-specific maintenance.
